## 2. Поднятые сервисы — и почему именно они

`docker ps`: lakehouse-minio, lakehouse-pg, lakekeeper, trino. Spark запускался отдельным контейнером на время задачи п.6.2.

| Сервис | Версия | Роль в стеке | Почему именно он (а не альтернатива) |
|---|---|---|---|
| MinIO | RELEASE 2025-05-24 (образ bitnamilegacy/minio) | S3-совместимое объектное хранилище (сюда физически падают parquet-файлы) | Это S3 у себя на компьютере: Trino, Spark и Lakekeeper работают с ним как с облаком, и потом всё можно перенести в настоящий S3. Бесплатный, ставится одним контейнером. Официальный образ отдаёт 401, поэтому взяла bitnamilegacy/minio, это тот же MinIO. |
| PostgreSQL | 17.11 | БД, где Lakekeeper хранит метаданные каталога | Lakekeeper умеет хранить каталог только в Postgres. И это логично: каталог должен менять "текущую версию таблицы" целиком или никак, а это как раз транзакции. |
| Lakekeeper | 0.14.0 | Iceberg REST Catalog — каталог метаданных таблиц | Открытый и лёгкий REST-каталог для Iceberg. Trino и Spark подключаются к нему одинаково, в п.6.2 Spark сразу увидел те же таблицы. Hive Metastore тяжелее и старее. |
| Trino | 476 | SQL-движок: ходит в Lakekeeper за метаданными и читает/пишет данные в MinIO | В нём есть генератор tpch, поэтому данные не надо качать. Все слои делаются обычным SQL, кодек меняется одной командой SET SESSION. И он быстрый: Q18 по Bronze 3-8 с, Spark на тех же данных 11-17 с. |
| Spark | 3.5.5 (tabulario/spark-iceberg) | второй движок поверх тех же Iceberg-таблиц (п.6.2) | Хотела проверить, что данные не привязаны к Trino. Spark читает те же таблицы сам, через Lakekeeper. В образе tabulario/spark-iceberg уже всё собрано, ничего докачивать не пришлось. |

### Скрипты, которыми поднимал стек

Полностью - `stand/up.sh` (одна команда `cd stand && ./up.sh`). Основное:

```bash
# MinIO - объектное хранилище. Консоль на 9101, т.к. порт 9001 на маке занят
docker run -d --name lakehouse-minio --add-host host.docker.internal:host-gateway \
  -p 9000:9000 -p 9101:9001 \
  -e MINIO_ROOT_USER=minioadmin -e MINIO_ROOT_PASSWORD=minioadmin \
  -v minio-data:/bitnami/minio/data bitnamilegacy/minio:latest

# PostgreSQL - метаданные Lakekeeper. Порт 5433, т.к. на 5432 уже работает локальный postgres
docker run -d --name lakehouse-pg --add-host host.docker.internal:host-gateway \
  -e POSTGRES_PASSWORD=postgres -p 5433:5432 \
  -v pg-data:/var/lib/postgresql/data postgres:17

# Lakekeeper - сначала migrate (создаёт таблицы в postgres), потом serve
PG='postgresql://postgres:postgres@host.docker.internal:5433/postgres'
docker run --rm --add-host host.docker.internal:host-gateway \
  -e 'LAKEKEEPER__PG_ENCRYPTION_KEY=This-is-NOT-Secure!' \
  -e "LAKEKEEPER__PG_DATABASE_URL_READ=$PG" -e "LAKEKEEPER__PG_DATABASE_URL_WRITE=$PG" \
  quay.io/lakekeeper/catalog:latest migrate
docker run -d --name lakekeeper --add-host host.docker.internal:host-gateway \
  -e 'LAKEKEEPER__PG_ENCRYPTION_KEY=This-is-NOT-Secure!' \
  -e "LAKEKEEPER__PG_DATABASE_URL_READ=$PG" -e "LAKEKEEPER__PG_DATABASE_URL_WRITE=$PG" \
  -p 8181:8181 quay.io/lakekeeper/catalog:latest serve

# дальше в up.sh: bootstrap Lakekeeper, бакеты bench/bronze/silver/gold в MinIO (через mc)
# и по warehouse в Lakekeeper на каждый бакет (через REST API /management/v1/warehouse)

# Trino - свой jvm.config (heap 4 ГБ) и config.properties (лимит памяти запроса 2 ГБ + spill)
docker run -d --name trino --add-host host.docker.internal:host-gateway -m 5500m -p 8080:8080 \
  -v "$(pwd)/catalog:/etc/trino/catalog" \
  -v "$(pwd)/conf/jvm.config:/etc/trino/jvm.config" \
  -v "$(pwd)/conf/config.properties:/etc/trino/config.properties" \
  trinodb/trino:476
```

Каждый слой - отдельный бакет в MinIO, отдельный warehouse в Lakekeeper и отдельный каталог в Trino (`stand/catalog/bronze.properties`, `silver.properties`, `gold.properties`). Пятый каталог `bench` - для бенчмарка, `tpch` - генератор исходных данных.

Что пошло не по гайду:
- Официальный образ `quay.io/minio/minio` отдаёт 401, взяла `bitnamilegacy/minio`.
- На маке уже занят 5432 (локальный postgres) и 9001 (другая программа) - перенесла порты на 5433 и 9101.
- Trino упал с `java.lang.OutOfMemoryError: Java heap space` на сверочном запросе (Q18 по генератору tpch, CTE считался 3 раза из-за EXCEPT). Переписала сверку на один FULL JOIN и снизила лимит памяти запроса до 2 ГБ, чтобы оставался запас heap.
- Trino и Spark одновременно в 7.6 ГБ памяти Docker не помещаются - Spark запускала при остановленном Trino.

## 3. Разбор запроса — какие данные нужны

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
|---|---|---|
| lineitem | orderkey, quantity | подзапрос: `sum(quantity)` по orderkey, `HAVING > 300` - отбор крупных заказов; в основном запросе `sum(quantity)` = total_quantity (вывод); orderkey - джойн с orders |
| orders | orderkey, custkey, orderdate, totalprice | orderkey - джойн с lineitem и фильтр `IN (подзапрос)`; custkey - джойн с customer; orderdate, totalprice - группировка, сортировка (`totalprice DESC, orderdate`) и вывод |
| customer | custkey, name | custkey - джойн с orders; name - группировка и вывод |

Для обогащения в Silver дополнительно взяла `nation` (nationkey, name) - название страны клиента. Для нормализации в Silver взяла ещё три поля, которые сами по себе Q18 не нужны, но хранятся "склеенными": `customer.phone`, `orders.orderpriority`, `orders.clerk`. Остальные колонки (адреса, комментарии, даты отгрузки и т.д.) дальше Bronze не идут.

Что сделано в Silver:
- очистка: отбрасываются строки с NULL в ключах, позиции с `quantity <= 0`; клиенты дедуплицируются по custkey (`row_number()` по последней загрузке) - в сгенерированных данных дублей и мусора нет, число строк не изменилось;
- нормализация: в трёх полях было склеено по два значения, разложила их на отдельные колонки:
  - `phone` "25-989-741-2988" -> `phone_country_code` 25 и `phone_number` "989-741-2988";
  - `orderpriority` "1-URGENT" -> `priority_level` 1 и `priority_name` URGENT;
  - `clerk` "Clerk#000000951" -> `clerk_id` 951 (префикс одинаковый у всех, информации не несёт);
  - плюс `trim` строк, сегмент в верхний регистр, деньги из double в `decimal(12,2)`, количество в integer;
- обогащение: у клиента - название страны из nation; у заказа - `total_quantity` (сумма quantity по позициям) и `line_cnt` (число позиций). Это и есть подзапрос Q18, посчитанный один раз для всех 15 млн заказов. Из 60 млн строк lineitem (1 464 МБ) получилось 15 млн строк заказов (196 МБ).

Проверка нормализации (в `sql/medallion.sql`, результат `results/silver_checks.txt`): пустых значений после разбора 0, код страны в телефоне у всех 1.5 млн клиентов равен `nationkey + 10` (0 несовпадений, 25 кодов), приоритетов 5, клерков 10 000.

Честно про размер: после нормализации Silver стал тяжелее. dim_customer был 13.75 МБ без телефона, стал 23.89 МБ - номера телефонов почти все разные и плохо сжимаются. fct_orders вырос со 161 до 196 МБ из-за трёх новых колонок. Зато теперь можно фильтровать и группировать по уровню приоритета или стране телефона обычным `=`, а не через `LIKE` и разбор строки. Gold от этого не изменился и по-прежнему совпадает с Q18.

## 5. Тесты производительности

Методика:
- каждый вариант - те же три таблицы, что нужны Q18 (customer, orders, lineitem из `tpch.sf10`), пишутся в отдельную схему `bench.<формат>_<кодек>`; кодек задаётся `SET SESSION bench.compression_codec` перед `CREATE TABLE`;
- размер - сумма `file_size_in_bytes` из `$files`; время - `elapsedTime` из статистики Trino;
- холодный прогон: перезапуск `trino` и `lakehouse-minio` + сброс page cache в виртуалке Docker (`echo 3 > /proc/sys/vm/drop_caches`), иначе только что записанные файлы читаются из памяти; тёплый - сразу второй прогон;
- для GZIP и ZSTD прогоны повторены 3 раза, в таблице медиана (`scripts/bench_repeat.py`, `results/bench_repeat_sf10.csv`).

| Сжатие на Bronze | Время запроса | Размер Bronze, МБ | Твой вывод (что лучше и почему) |
|---|---|---|---|
| GZIP | cold 6.18 с / warm 3.77 с (медиана из 3; cold 5.53-6.29) | 1 896.4 | Для Bronze взяла GZIP: он самый маленький, а по скорости запроса с ZSTD почти одинаково (разница меньше, чем между двумя прогонами). Пишется дольше, но Bronze пишут редко. |
| ZSTD | cold 6.53 с / warm 5.09 с (медиана из 3; cold 4.88-6.78) | 1 942.6 | Больше GZIP всего на 2.4%, зато пишется почти вдвое быстрее (44.9 с против 78.7). Поэтому его поставила на Silver. Если бы Bronze грузился каждый день, тоже взяла бы ZSTD. |

Запись: GZIP 78.7 с, ZSTD 44.9 с (GZIP в 1.75 раза дольше). ZSTD больше GZIP на 2.4%.

Повторный полный прогон бенчмарка на пересобранном с нуля стенде - `results/bench_bronze_sf10_run2.csv`:
- размеры совпали до 0.1 МБ, число файлов то же, время записи отличается не больше чем на 5 с (GZIP снова самый медленный: 80.3 с);
- выброс orc_none не повторился: cold 8.18 с;
- Q18 cold без выбросов 5.5-8.2 с; GZIP и ZSTD поменялись местами (5.51 и 5.47 с против 6.30 и 6.58 в первом прогоне), то есть разница между ними меньше разброса между прогонами.

Что видно из таблицы:
- сжатие относительно NONE: Parquet SNAPPY -46.9%, GZIP -62.3%, ZSTD -61.4%; ORC SNAPPY -50.8%, GZIP -65.0%, ZSTD -64.1%;
- ORC больше Parquet на том же кодеке: на 2.5-2.7% со сжатием и на 10.6% без сжатия (при этом customer и orders в ORC меньше, а lineitem больше);
- по записи: самый медленный GZIP (Parquet 78.7 с, ORC 64.7 с), остальные - 37-54 с; NONE не самый быстрый на запись в ORC (54.3 с против 49.1 у SNAPPY);
- по чтению: несжатые варианты не быстрее сжатых, разница между кодеками со сжатием - в пределах шума (около 1 с).

Выводы по бенчмарку:
- Без сжатия хуже во всём: данных в 1.9-2.9 раза больше, а запрос не быстрее. Читать лишние байты с диска дольше, чем распаковать.
- GZIP и ZSTD почти одинаковые по размеру и по чтению, отличаются только записью. SNAPPY больше в 1.4 раза.
- Parquet чуть меньше ORC, по скорости одно и то же. Взяла Parquet: его читают все движки, и в Iceberg он по умолчанию.
- Размеры при повторе совпали до 0.1 МБ, а время скачет на 1-2 с, иногда до 30 с, когда Trino не хватает памяти. Так что по одному прогону про скорость судить нельзя, нужно несколько и брать медиану.

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ |
|---|---|
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | В обычной БД данные лежат в её собственном формате и на её дисках, и растить её дорого. В lakehouse файлы лежат в дешёвом S3 в открытом формате, а движок отдельно. У меня одни и те же таблицы читали и Trino, и Spark, без копирования. А Iceberg даёт то, чего у простой папки с файлами нет: транзакции, схему, снапшоты, откат. |
| Пример schema evolution на Silver: добавил/переименовал колонку - что произошло? | Обе команды прошли мгновенно: файлы не переписывались, поменялись только метаданные. У старых строк в новой колонке NULL. После переименования старые данные читаются под новым именем - Iceberg помнит колонки по id, а не по имени. Подробно ниже. |
| Пример скрипта восстановления данных из снапшота (time travel) | см. ниже |

Что сделала на `silver.lakehouse.dim_customer` (скрипт `scripts/evolution.sh`, полный вывод `results/evolution_output.txt`):

1. `ALTER TABLE ... ADD COLUMN vip boolean` - у всех строк vip = NULL, файлов как было 2, так и осталось, новый снапшот не появился.
2. `UPDATE ... SET vip = true WHERE custkey IN (клиенты с заказами > 300)` - 623 клиента (на 624 крупных заказа, у одного клиента их два); появился снапшот `overwrite`.
3. `ALTER TABLE ... RENAME COLUMN name TO customer_name` - старые данные сразу читаются под новым именем, файлы не переписывались, снапшот не появился.

Восстановление из снапшота:

```sql
-- запомнили текущий снапшот
```

### 6.2. Подключить инструмент к lakehouse

| Инструмент | Почему выбрал именно его |
|---|---|
| Spark 3.5.5 (образ tabulario/spark-iceberg) | Spark читает Iceberg сам, через тот же Lakekeeper, без Trino - так нагляднее, что данные открытые. Metabase или Superset всё равно ходили бы через Trino. Для моего запроса Trino быстрее (3-8 с против 11-17 с), а Spark больше подходит для больших пакетных расчётов. |

Запуск (Trino перед этим остановлен):

```bash
docker run --rm --name p1-spark --add-host host.docker.internal:host-gateway \
  -m 5g --entrypoint spark-submit \
  -e AWS_REGION=us-east-1 -e AWS_ACCESS_KEY_ID=minioadmin -e AWS_SECRET_ACCESS_KEY=minioadmin \
  -v "$(pwd)/scripts/spark_bronze.py:/home/iceberg/spark_bronze.py" \
  tabulario/spark-iceberg:latest --driver-memory 3g /home/iceberg/spark_bronze.py
```

Подключение - `scripts/spark_bronze.py`: каталог `bronze` типа `rest` на `http://host.docker.internal:8181/catalog`, warehouse `bronze`, S3FileIO на MinIO. `spark.sql.defaultCatalog = bronze`, потому что в образе по умолчанию прописан каталог `demo`, которого у нас нет.

Что Spark увидел в Bronze (вывод - `results/spark_output.txt`):
- `SHOW TABLES` - raw_customer, raw_orders, raw_lineitem, raw_nation;
- строк 1 500 000 / 15 000 000 / 59 986 052 / 25 - как в Trino;
- в схеме raw_orders есть служебные loaded_at и source_system;
- снапшоты Iceberg (`raw_lineitem.snapshots`) - тот же snapshot_id, что в Trino;
- Q18 по Bronze в Spark: 100 строк, сумма total_quantity 30 977, первая строка Customer#001287812 / заказ 42290181 / 558289.17 - то же, что Gold в Trino. Время 11.3 с, в прошлых запусках 11.4 и 17.0 с (в Trino по тем же данным 3.4-7.8 с).

## 7. Выводы

Медальон удобен тем, что тяжёлая работа делается один раз: Silver превратил 60 млн строк lineitem в 15 млн заказов с готовым количеством, и Gold из 100 строк читается за доли секунды. Bronze при этом хранит всё как было, так что ошибку всегда можно пересчитать. Кодек я выбирала под слой: GZIP где важно место, ZSTD где часто пересобирают, SNAPPY где часто читают. Неожиданным было, что без сжатия запрос не быстрее, а данных в 2-3 раза больше. Gold совпал с оригинальным Q18, и Spark дал тот же ответ - значит, слои собраны правильно.
